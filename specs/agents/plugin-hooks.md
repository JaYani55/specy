# Plugin Hook System — Full Target Reference

Authoritative documentation of every plugin hook target in Specy: target name,
scope, kind, dispatch point, context shape, and implementation status. This
document is the **contract registry** — every new hook target must be added
here (see [Adding a new hook target](#adding-a-new-hook-target)).

Source of truth for context types: `api/lib/*Hooks.ts` (API scope) and the
consuming service modules in `src/services/` / `src/utils/` (UI scope).
The `hook_metadata` array in a plugin's `plugin.json` is **descriptive only** —
executable handlers are wired at build time via the generated registries.

---

## 1. Architecture

### 1.1 Core provides, plugins implement

Per the EUPL provider/implementer model (`specs/plugins/eupl-compliance.md`),
the core defines **empty hook slots** (targets). Plugins fill them with
handlers. Plugins never modify core code; all coupling is interface-only.

### 1.2 Build-time integration

Handlers are statically imported at build time (no runtime plugin loading):

| Registry | Generated by | Consumed by |
|---|---|---|
| `src/plugins/registry.ts` | `scripts/register-plugins.mjs` | Frontend plugin entrypoints |
| `src/plugins/hooks-registry.ts` | `scripts/register-plugins.mjs` | `getPluginHooks(target, userRoles)` |
| `api/plugin-hooks.ts` | `scripts/register-plugins.mjs` | `getRegisteredApiPluginHooks()` |

**Scope separation is strict:** `getPluginHooks` (frontend, `src/plugins/loader.ts`)
walks only `PluginDefinition.hooks` — the UI entries of the generated registry.
API-scope handlers from `api/plugin-hooks.ts` never appear there, and vice
versa. A handler whose `scope` does not match the dispatch point is inert.

### 1.3 Scope and kind

- **`scope: "ui"`** — handler lives in the plugin frontend entrypoint
  (`PluginDefinition.hooks`), dispatched client-side via
  `getPluginHooks(target, userRoles)`. Visibility is filtered by user roles.
- **`scope: "api"`** — handler lives in the plugin's API entrypoint
  (`api_hooks_entrypoint`), dispatched server-side via the generated
  `api/plugin-hooks.ts` registry.
- **`kind: "transform"`** — the handler receives the accumulated context and
  returns the (possibly modified) context. Handlers run sorted by `order`
  (ascending, default `100`); the result of one handler feeds the next.
- **`kind: "observer"`** — the handler performs side effects; the return value
  is ignored. Used for event-driven targets (`queue.message`).

### 1.4 Handler contract

```typescript
interface PluginHookContribution<TContext, TResult> {
  key: string;            // Unique within the plugin, e.g. "pluradash-mcp-kb-tools"
  target: string;         // Core target identifier, e.g. "mcp.tools"
  scope: 'ui' | 'api';
  kind: 'transform' | 'observer';
  order?: number;         // Sort key within the target, default 100
  description?: string;
  handler: (context: TContext) => TResult | Promise<TResult>;
}
```

Error semantics: transform chains do **not** catch handler exceptions — a
throwing handler propagates to the core dispatch point and fails the enclosing
request/cron run (fail-fast). The sole exception is `queue.message`, where the
dispatch wraps each handler in `ctx.waitUntil(...).catch(...)` and logs the
failure without breaking other handlers or the `ackAll()`.

### 2.4 Declared but not wired ⚠️

These targets exist in `plugin.json` → `hook_metadata` (and therefore in the
generated `api/plugin-metadata.ts`), but have **no dispatch point in core and
no executable handler**. They are aspirational declarations — do not rely on
them until wired:

| Target | Declared by | Intended semantics (per manifest description) | Missing for wiring |
|---|---|---|---|
| `system.scheduled` (api, observer) | PluraDash `pluradash-kb-scheduled-sync` | Cron-triggered processing of pending KB sync/embedding jobs | Core `scheduled()` handler must fan out to registered `system.scheduled` hooks (today it only runs core form reminders); a `ScheduledHookContext` type in `api/lib/` |
| `workspace.organization` (ui, transform) | PluraDash `pluradash-organization-workspace` | Provide organization/workspace administration surface | Core invocation site + context type; the org admin surface is currently provided via plugin routes/admin sections instead |

> Knowledge-base sync actually runs **on-demand** (`knowledgeBase.sync.invoke`
> + MCP tools), not via cron — so the missing `system.scheduled` wiring does
> not currently break PluraDash behavior, but the manifest promise is unfulfilled.

## 3. Gaps found during documentation (2026-09-09 audit)

### 3.1 Dead collectors ❌

Five API-scope collectors are defined but never invoked from any route or
service — hooks registered against these targets are inert even when
implemented: `knowledgeBase.sync.sources`, `knowledgeBase.prompt.context`,
`knowledgeBase.settings.sections`, `knowledgeBase.settings.visibility`,
`admin.connections.sections`. Fix on the core side: wire the collectors into
the consuming routes (KB routes, admin connections page) or remove the targets.

### 3.2 Scope mismatch ⚠️

`isibot.flow.types` is dispatched **UI-side only** (`src/services/isibotFlowTypes.ts`
walks the frontend registry), but PluraDash implements it as **api scope**
(`api/storageHooks.ts`) — that handler can never run because the frontend
registry contains no API handlers. The target needs either a UI-scope handler
in the plugin or an API dispatch that serves descriptors to the builder.

### 3.3 Metadata drift

`hook_metadata` in `plugin.json` is descriptive only and currently diverges
from the implemented handlers in both directions:

- Declared without handler/dispatch: `system.scheduled`, `workspace.organization`
- Implemented without declaration: `knowledgeBase.entity.actions`,
  `knowledgeBase.entity.afterCreate` (ui), `knowledgeBase.sync.invoke` (api)

Keep `hook_metadata` in sync when touching the manifest.

## 4. Case study: PluraDash

PluraDash (`plugins/pluradash/`, separate gitignored repo) declares **18
hooks** in `hook_metadata` and implements **19 handlers** (7 UI in
`src/index.tsx`, 12 API targets in `api/storageHooks.ts`) — including the
event-driven `queue.message` target (SMS notifications via Twilio) and the
unwired `system.scheduled` declaration. It demonstrates every hook category:

- **UI composition:** landing-page option/resolve/path, forms builder provider label, media URL rewriting
- **MCP agent surface:** support-gated KB tools + workspace app-sync tools (`mcp.tools`)
- **Integration hub:** Isibot flow node types, GitHub App sync (via MCP tools + `sync.invoke`), Twilio SMS (`queue.message`)
- **Storage:** tenant storage policy/sources, forms file upload provider + notification links
- **Admin composition:** AI services section (`adminSections` manifest field; the `admin.connections.sections` hook target is currently inert, §3.1)

In Specy, "plugin" behaves like an application module and integration hub
(Specy ↔ PluraPi ↔ isibot-fon ↔ GitHub ↔ Twilio) — agents consume the plugin
surface as first-class clients via the MCP tools registered through `mcp.tools`.

## 5. Adding a new hook target

### 5.1 Core side

1. Create/extend an `api/lib/<domain>Hooks.ts` (API) or a service module
   (UI) with: the `TARGET` constant, a `...HookContext` interface, and a
   runner that sorts hooks by `order` and chains the context.
2. **Invoke the runner** at the extension point in core routes/components —
   a collector without a call site is dead code (see §3.1).
3. Document the target **in this document** (§2 table row) — this is a hard
   requirement (see AGENTS.md §4).

### 5.2 Plugin side

1. Implement the handler in the plugin entrypoint (`hooks` array, UI scope)
   or API hooks entrypoint (API scope) — with the correct `scope` (§1.2).
2. Add a matching `hook_metadata` entry in `plugin.json` (descriptive, keep in
   sync — see §3.3).
3. Declare any required infrastructure via `wrangler_bindings` (see
   `specs/plugins/development.md` §3.1).

### 5.3 Event-driven targets

Event-driven targets (`*.scheduled`, `queue.message`, future webhook targets)
use `kind: "observer"`. Their dispatch points live in the Worker entrypoint
(`api/index.ts` `scheduled()` / `queue()`) and must provide per-handler error
isolation so one failing plugin cannot starve the batch or break the cron run.
