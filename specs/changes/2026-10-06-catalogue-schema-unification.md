# Catalogue schema unification

## Summary

The separate `service-product` and `event` schema purposes are merged into **one catalogue concept**: a catalogue schema (stored kind `event`) holds both the product's canonical page and its event pages. Pages are classified by their linked aggregate — a `mentorbooking_products` row owning the page as `product_page_id`, or a `mentorbooking_events` row linking the page as `page_id` — not by the schema kind alone.

The user-facing flow becomes exactly: create a product → connect it to a catalogue schema → create events for the product → the event pages are created in the same catalogue.

## Compatibility answer

Nothing breaks for existing data:

- Regular `page` schemas are untouched; their pages keep generic page behavior.
- Existing event schemas keep working unchanged — `event` is now the catalogue kind and all event-side checks still match.
- Existing `service-product` schemas are migrated to `event` by the migration; their product pages, aggregates and delivery keep working through the relaxed product RPCs.
- The `page_schemas_entity_kind_check` constraint still accepts the legacy value so the migration stays idempotent and backups remain loadable.

## Impact analysis

### Database

One migration (`202610060001_catalogue_schema_unification.sql`):

- Migrates `entity_kind = 'service-product'` schemas to `event` (bumps `definition_revision` via the existing trigger).
- Product aggregate RPCs (create/update/publish/archive, custom-fields update, schema reassignment, product deletion) accept catalogue schemas and set `specy.event_page_write = 'on'` around their page writes so the page guards allow them.
- Page ownership guards now treat catalogue pages as owned by either an event or a product (never both): `validate_service_product_page_owner` drops the event-kind rejection and adds the mutual-exclusion check, `enforce_event_page_link` allows product-owned pages, `guard_event_page_mutation` still requires the aggregate service for event-owned pages but allows orphan page deletion and schema reassignment.

### Runtime

- Event creation now offers every catalogue schema of the workspace (product schemas included).
- Public collection delivery of a catalogue lists event pages with event relations and product pages with product relations; single-page delivery classifies per page.
- The schema editor presents one catalogue purpose; the previous "Produktschema"/"Veranstaltungsschema" distinction disappears from the UI.

### API surface

- Event page create/update endpoints and the matching MCP tools accept catalogue schemas.
- Catalogue schemas advertise `supported_includes: entity, event, product`.

## Known follow-up

A dedicated "connect an existing page-less product to a catalogue" flow (RPC + UI) is not part of this change; products created through the legacy form keep operating without a canonical page, and product creation with a catalogue page remains available through the product aggregate create API.
